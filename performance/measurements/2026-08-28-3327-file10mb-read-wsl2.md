## Notes

First WSL2 file-content read measurement on `3327` at this size. **Clear monotonic upward trend**
(64 -> 74 -> 100 -> 108 -> 118, +84% peak-to-last) - the opposite direction from every create-side
trend seen in this session, and explained by how `file10mb-read.sh` itself indexes: each run's
`ops` counter restarts at 0, so `idx = (ops % total) + 1` re-reads the *same* low-numbered files
(1, 2, 3, ...) from the start in every run, extending a little further as each run's ops count
grows. The ~52.5 GB tree exceeds this machine's 32 GB RAM (per `../machines.md`), so the tree as a
whole cannot be fully page-cache-resident, but the low-index subset actually touched (at most
~2,362 files, ~23.6 GB across all 5 runs combined) fits comfortably - each run finds progressively
more of "its" range still warm from the previous run's pass over the same range, producing the
trend. This is an artifact of the read script's indexing, not a filesystem-level warmup effect -
worth fixing in the script (e.g. continuing the index across runs, or picking pseudo-random
indices the way `dir-lookup.sh` does) if a cleaner 10 MB read number is needed later.

Mean read throughput (92.8 ops/s, ~928 MB/s) is noticeably above the matching create's 52.0 ops/s
(~520 MB/s) - unlike native Windows on this same machine, where 10 MB reads were *slower* than
creates once the working set exceeded the OS cache (see
`2026-08-28-3327-file10mb-read-native.md`'s Notes). Given the indexing artifact above, this
comparison is confounded and should not be read as "WSL2 reads faster than it creates at 10 MB" -
a large fraction of these reads were partially cache-warm by construction, not by genuine
disk-bound throughput.
