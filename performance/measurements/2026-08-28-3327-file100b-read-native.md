- Machine: 3327
- Execution environment: native Windows (Windows 11 Enterprise, 10.0.26200), Windows PowerShell 5.1
- Power profile: base scheme `aeeed979-846d-4e51-bb46-e7b4f140eb43` ("Thieme Energy Options", a
  custom/renamed Windows scheme, not one of the stock named profiles), AC power-mode overlay

  background activity was not observed or controlled. Scripts were run one at a time, sequentially.

## Workload
- Operation: 100 B file read-back, cycling over the files `file100b-create.ps1` left behind
- Location: native
- Tool: PowerShell `[System.IO.File]::ReadAllBytes` (result discarded via `$null =`), via
  `performance/scripts/file100b-read.ps1`
- Mode: sequential
- Window: 20 s
- Scale: reads cycle over the ~47,700-file dataset from `file100b-create` (~4.8 MB total, fits
  entirely in the OS file cache); ~23,000-41,500 reads per run
- Content: 100 B/file

## Notes

First measurement of this workload anywhere.

Reads run roughly 3x faster than the corresponding 100 B *creates* (~1562 vs ~477 ops/s). The
whole dataset is a few MB, so this is a warm-cache measurement - the disk is not involved after the
first pass; the number is essentially the cost of a `[System.IO.File]::ReadAllBytes` call plus loop
overhead in PowerShell.

**Wide, upward-drifting spread** (1144 -> 2076, range factor 1.8x). No deliberate isolation and a
corporate-managed OS with background activity is the most likely cause; a genuine cache-warming
ramp over the first run or two is also plausible. Treat the mean as approximate. A repeat under
quieter conditions would be worth having before drawing conclusions from this one.
