# 30 KB file creation - native - 3327/WSL2 Ubuntu 24.04/local SSD

## Setup
- Date: 2026-08-28
- Machine: 3327
- Execution environment: WSL2, Ubuntu 24.04.4 LTS. Working directory
  `~/dedupfs-perf/files30kb` - WSL2's own native filesystem, not `/mnt/c/...`.
- Power profile: base scheme `aeeed979-846d-4e51-bb46-e7b4f140eb43` ("Thieme Energy Options", a
  custom/renamed Windows scheme, not one of the stock named profiles), AC power-mode overlay
  `961cc777-2547-4f9d-8174-7d86181b8a7a` = `OVERLAY_SCHEME_MIN` ("Besseres Overlay für
  Akkulaufzeit" / "Best power efficiency"). On AC power (plugged in), developer-confirmed at the
  start of this session.
- IO device: local SSD (WSL2's own ext4 virtual disk, backed by the host's NVMe SSD per
  `../machines.md`)
- DedupFS build: `deadac0e` on `rust-performance-test-idea` - native filesystem baseline, no
  DedupFS code exercised; recorded only to pin which script version was run.
- Isolation: none taken deliberately - ran as the sole foreground command in an otherwise idle
  WSL2 session; host-side background activity was not controlled or observed.

## Workload
- Operation: File creation at 30 KB, unique content
- Location: native
- Tool: bash redirection, content from `perf-gen` (`../scripts/file30kb-create.sh`,
  `cargo build --release -p perf-gen` run by the script itself)
- Mode: sequential
- Window: 20 s
- Scale: 87,858 files total across the 5 runs (15,690-18,731 per run, time-boxed not
  count-fixed), spread round-robin across 20 subdirectories under `~/dedupfs-perf/files30kb`,
  first measurement against this tree; ~2.7 GB written in total.
- Content: 30 KB, unique per file (`perf-gen`-generated, see `../methodology.md`'s "File-content
  workloads")

## Notes

First WSL2 file-content measurement on `3327` at this size. Run 1 is close to the runs-2-5 median
(~899.5), no warmup pattern - kept. Noisier than the 100 B run above (784-936 vs. 933-979), no
clear trend across runs (dips at run 2, not monotonic).

Similar throughput to the 100 B create result on this machine (878.0 vs. 954.0 ops/s, ~8% lower
despite 300x the content) - the same "per-call/generator overhead, not content size, dominates
below some size" pattern `../overview.md` already notes for `3327`'s native-Windows results at
these sizes.

Roughly 9x `julius`'s own WSL2 result for this workload (878.0 vs. 93.6 ops/s, see
`2026-08-28-julius-file30kb-create-wsl2.md`) - essentially the same machine-to-machine ratio as
100 B creation showed (~9x) on this pair of machines, consistent with both sizes being dominated
by the same per-call cost rather than by content-size-dependent work.
