# 100 B file creation - native - 3327/WSL2 Ubuntu 24.04/local SSD

## Setup
- Date: 2026-08-28
- Machine: 3327
- Execution environment: WSL2, Ubuntu 24.04.4 LTS. Working directory
  `~/dedupfs-perf/files100b` - WSL2's own native filesystem, not `/mnt/c/...`.
- Power profile: base scheme `aeeed979-846d-4e51-bb46-e7b4f140eb43` ("Thieme Energy Options", a
  custom/renamed Windows scheme, not one of the stock named profiles), AC power-mode overlay
  `961cc777-2547-4f9d-8174-7d86181b8a7a` = `OVERLAY_SCHEME_MIN` ("Besseres Overlay für
  Akkulaufzeit" / "Best power efficiency"). On AC power (plugged in), developer-confirmed at the
  start of this session.
- IO device: local SSD (WSL2's own ext4 virtual disk, backed by the host's NVMe SSD per
  `../machines.md`)
- DedupFS build: `deadac0e` on `rust-performance-test-idea` - native filesystem baseline, no
  DedupFS code exercised; recorded only to pin which script version was run.
- Isolation: none taken deliberately - ran as the sole foreground command in an otherwise idle
  WSL2 session; host-side background activity was not controlled or observed.

## Workload
- Operation: File creation at 100 B, unique content
- Location: native
- Tool: bash redirection, content from `perf-gen` (`../scripts/file100b-create.sh`,
  `cargo build --release -p perf-gen` run by the script itself)
- Mode: sequential
- Window: 20 s
- Scale: 95,457 files total across the 5 runs (18,679-19,588 per run, time-boxed not count-fixed),
  spread round-robin across 20 subdirectories under `~/dedupfs-perf/files100b`, first measurement
  against this tree.
- Content: 100 B, unique per file (`perf-gen`-generated, see `../methodology.md`'s "File-content
  workloads")

## Notes

First WSL2 file-content measurement on `3327` at this size - closes a coverage gap
(`../overview.md` previously had `3327` native-Windows rows for this workload but no WSL2 rows at
any size). Mild, monotonic downward drift across the 5 runs (966 -> 979 -> 950 -> 942 -> 933,
excluding the slight run-1/run-2 bump) - the same "tree grows, creation slows" pattern
`../overview.md` already notes for `julius`'s larger-file WSL2/native runs, here visible even at
100 B; not investigated further.

Roughly 9x `julius`'s own WSL2 result for this workload (954.0 vs. 107.0 ops/s, see
`2026-08-28-julius-file100b-create-wsl2.md`) - a much larger machine-to-machine ratio than
directory creation or zero-byte-file creation showed (~2.4x, ~1.5x) on this same pair of
machines. Not investigated further; a `perf-gen` process-spawn cost that scales differently with
CPU generation than a plain `mkdir`/`touch` syscall is one plausible contributor, alongside the
general hardware gap `../machines.md` describes.
